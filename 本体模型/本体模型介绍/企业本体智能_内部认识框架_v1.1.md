## 导读：为什么把 Agent 接入数据库仍然不够

### 从一个具体问题开始

假设一家制造企业已经把 ERP、CRM、MES、采购、合同和企业文档全部连接给一个 Agent，然后向它提出一个问题：

> 某个重要客户临时增加订单，我们能不能按时交付？应该怎样调整生产和采购？

Agent 可以查到客户、订单、库存、设备、供应商和合同等数据，但取得这些数据，并不等于理解了问题。它还需要知道：

- 不同系统中的名称是否指向同一个客户；
- 库存中哪些可以使用，哪些已经被其他订单占用；
- 订单、产品、物料、生产线和供应商之间如何关联；
- 这个客户是否具有特殊优先级；
- 哪些安全库存、质量和生产约束不能突破；
- 当前采用的是哪个版本的规则；
- 可以调用哪些预测、排产和优化模型；
- 哪些调整可以建议，哪些必须经过人工审批；
- 最终建议依据了什么数据、规则、权限和模型。

数据库保存了大量记录，却不一定显式告诉 Agent：这些数据在业务上代表什么、彼此如何关联、为什么产生、根据什么规则变化，以及谁有权采取什么行动。

聪明的 Agent，只是相当于有个聪明的大脑。只有当它处在能够把其对象的业务流程、数据逻辑以及行动能力连接起来的时候，才能发挥价值。

这种连接就像是人类和智能体共享这个世界的底层架构。这时候，模型就不只是停留在聊天界面里，而是可以自动化工作。解决实际问题，而且要遵守管理规范，可审计。

这就是企业本体要处理的基本问题。

### 一句话解释本体模型

面向初次接触者，可以暂时把本体模型理解为：

> **围绕特定问题，为人和 AI 建立一套边界清楚、语义相对稳定、可以持续修订的业务世界模型。**

它不是另一个数据库，也不是把全部企业数据重新保存一遍。更准确地说，是先建立一个由业务对象、属性、关系和语义限制组成的共同世界，再把不同数据库、文档和业务系统映射进这个世界。

这里的“稳定”不是永远不变，而是关键对象、关系和口径不会随单次问答任意漂移；当组织、制度和业务变化时，模型经过责任确认、版本管理和影响分析后受控修订。

### 日常所说的“本体模型”，实际上可能包含三个层次

| 层次 | 主要内容 | 解决的问题 |
|---|---|---|
| 企业或领域本体 | 对象类型、属性、关系、公理和语义限制 | 这个业务世界由什么构成 |
| 可操作语义层 | 实例、状态、事件、规则、函数、Actions、权限、来源和版本 | 如何查询、判断和改变这个世界 |
| 完整企业智能系统 | Agent、专业模型、工作流、业务系统和反馈校准 | 人和 AI 如何共同完成任务 |

本文严格区分这三个层次。日常讨论中如果宽泛使用“本体模型”，通常指的是前两个层次，而不是只有形式本体，也不是整个 AI 系统。

### Agent 如何在这个世界中工作

人提出问题和目标后，Agent 可以：

1. 识别问题涉及哪些对象和时间范围；
2. 查询对象的当前状态和原始证据；
3. 沿业务关系寻找影响路径；
4. 调用当前有效的规则、函数和专业模型；
5. 比较候选方案及其成本、风险和约束；
6. 提供带来源、假设和不确定性的建议；
7. 在权限范围内发起受控行动，或请求人工确认；
8. 根据实际结果校准原来的规则和模型。

因此，本体不是替 Agent 思考，也不保证 Agent 自动找到最优解。它规定的是 Agent 面对什么世界、可以使用什么能力、必须遵守什么边界，以及结论如何被检查。

只有目标可以计算、行动空间明确、约束充分，并具备可靠的预测、仿真或优化模型时，才适合讨论严格意义上的“最优解”。其他情况下，更现实的目标是形成有依据、可验证的可行方案或较优方案。

### 为什么要建设本体模型

#### 1. 串联系统，减少语义孤岛

即使 ERP、CRM、MES、WMS 和文档系统已经连接，同一个客户、订单、设备或指标仍可能采用不同标识和口径。本体把不同来源映射到共同对象和业务含义中，减少跨系统理解和重复解释成本。

本体不能单独完成数据接入、实体对齐和接口建设；它主要解决的是“系统连接以后，数据应当如何被共同理解”。

#### 2. 为 Agent 提供上下文和行动边界

数据库告诉 Agent 有哪些字段和值；本体及可操作语义层进一步告诉它：数据代表什么对象、对象如何关联、当前问题适用哪个口径、可以调用什么工具、当前身份能够执行什么动作，以及什么时候必须返回未知或请求人工判断。

#### 3. 建立审计与决策溯源

企业需要能够重建一次判断：当时提出了什么问题，使用了哪些证据，遵从了哪些规则，调用了什么模型和工具，使用了什么权限，谁进行了确认，最终执行了什么动作。

#### 4. 形成组织学习与持续反馈

通过行动记录、对象修改历史、执行 Trace、结果指标和人工反馈，企业可以识别有效模式、失败模式和异常路径，并将经过验证的经验反馈给业务、模型和工程团队。

### 一张图理解完整链条

```text
业务系统、文档、实时数据
            ↓
对象、属性、关系和共同口径
            ↓
实例、状态、事件和来源
            ↓
规则、函数、机理、预测和优化模型
            ↓
Agent 理解任务、查询证据、比较方案
            ↓
权限控制下的人工确认与 Actions
            ↓
实际结果、日志、审计和反馈校准
```

可以先记住三句话：

> **数据库保存企业记录了什么，本体说明这些记录在业务上意味着什么。**
>
> **本体告诉 Agent 它面对什么世界，Harness 告诉 Agent 它能够怎样工作，任务目标告诉 Agent 这一次要解决什么问题。**
>
> **企业智能不能只保存结论，还应保留从证据、规则和模型到决策、行动与结果的可重建学习闭环。**

## 核心共识

1. 企业本体是在特定业务边界内，对对象类型、属性、关系和语义限制所作的显式、可共享、可修订的概念模型。
2. 可操作语义层在本体基础上连接实例、状态、事件、规则、函数、Actions、权限、来源、版本和治理机制。
3. 企业本体智能是可操作语义层与 Agent、专业模型、工作流、业务系统和反馈校准形成的组合能力，不是一种单独模型。
4. 本体的直接价值是明确概念、组织关系、支持区分和有限推理；与其他能力结合后，可以改善协同、错误控制、审计和行动安全。
5. 本体不是数据库、知识图谱、数字孪生、因果模型、Agent 或 MCP 的同义词，也不能替代数据工程、专业模型和执行系统。
6. 企业不是静态对象集合。本体提供对象世界，事件和过程描述变化，规则和模型支持判断，Actions 改变状态，反馈检验原来的认识。
7. 本体不适用于所有 AI 应用，应优先用于跨系统、强关系、强约束、高风险、需行动或需审计的场景。
8. 企业知识必须区分记录、事实、规则、推导、预测、假设、候选、人的判断、未知和冲突，不能把模型输出直接写成企业事实。
9. 本体不是中立资产。关键定义可能影响指标、权限和责任，必须有明确的提出、审核、发布和修订机制。
10. 本体质量应通过能力问题、边界案例、反例、行动安全、维护成本和实际收益评价，而不是通过对象和关系数量评价。
11. 不应预设全企业只能有一个模型；局部共识、跨域映射和最小但有用，是更现实的建设方向。
12. 企业人工智能主权不等于所有技术都要自研，而是企业对关键数据、语义、模型、运行环境和技术选择保有实质控制权，并具备独立运行、评测、升级、回滚、迁移和替换的能力。
13. 企业本体智能不是一次性交付的软件。AI 系统自身需要持续演进和安全运行，并在条件具备时形成对企业运行、维护、经营和调度的持续诊断与行动指导能力。

完整企业智能可以概括为：

```text
证据与数据
+ 可治理的业务语义
+ 规则与专业模型
+ Agent 的任务协调
+ 受控行动
+ 权限、审计与反馈校准
+ 主权、持续运行与安全保障
```

## 一、企业本体是什么，又如何构建

### 1.1 从业务问题出发，而不是从描述整个企业出发

哲学中的本体论追问“什么存在、存在的本质是什么”。知识工程把它转化为一个工程问题：

> 在某个领域中，我们区分哪些事物，如何描述它们，它们之间有什么关系，又有哪些语义限制成立？

企业本体进一步收缩范围。它不试图描述整个世界，而是服务于特定业务目的。因此，建模的第一步不是盘点企业全部名词，而是明确一组能力问题：

- 谁要使用这个模型；
- 需要解决什么判断或行动问题；
- 必须区分哪些对象；
- 错误可能造成什么后果；
- 哪些知识值得长期维护。

例如，“某客户增单后能否按时交付”会要求模型表达客户、订单、产品、物料、库存、生产线、供应商及其关系；它不需要同时描述与这个问题无关的全部企业对象。

### 1.2 企业本体的基本组成

| 组成 | 回答的问题 | 示例 |
|---|---|---|
| 对象类型 | 有哪些类别的事物 | 客户、订单、物料、设备、岗位 |
| 实例 | 某个实际对象是谁 | 某客户、某张订单、某台压缩机 |
| 属性 | 对象具有什么特征 | 状态、产能、数量、生效时间 |
| 关系 | 对象如何连接 | 供应、负责、隶属、位于、占用 |
| 语义限制 | 哪些逻辑含义成立 | 上下位、等价、互斥、适用范围 |

企业本体不是简单术语表。术语表解释一个词，本体还要说明对象具有什么属性、与其他对象如何关联，以及哪些关系或组合不允许成立。

### 1.3 先建立业务对象世界，再映射数据

从企业对象出发，是一种重要且实用的建模方向。企业先明确对象定义、属性、关系、限制、来源和责任，再把不同来源的数据映射为这些对象的实例、状态和事件。

```text
业务问题与场景边界
        ↓
识别核心对象
        ↓
定义对象、属性、关系和语义限制
        ↓
映射数据库、文档和业务系统
        ↓
实体对齐、来源记录、时间管理和质量校验
        ↓
连接规则、模型、Actions、权限和治理
```

一个对象类型不是一个数据库。“供应商”的信息可能来自 ERP、采购、合同、风险平台和外部数据库；反过来，一个 ERP 数据库也可能同时存放供应商、订单、物料和库存。

```text
一个对象类型 ← 多个数据来源
一个数据库   → 多种对象类型
```

因此，不是把数据库连接成本体，而是先建立共同的业务对象世界，再把不同数据库映射进这个世界。

### 1.4 数据不会自然归入正确对象

随着业务运行，企业会持续产生数据，但这些数据不会自动、准确地归入本体。中间仍需完成：

- 字段与概念映射；
- 身份识别和去重；
- 主数据对齐；
- 状态同步；
- 时间和版本处理；
- 来源及责任记录；
- 质量校验和冲突处理。

错误的数据映射会制造新的语义问题。本体提供解释框架，不替代数据工程。

### 1.5 语义公理、数据验证和业务控制必须分开

```text
语义公理：某个表达在逻辑上意味着什么
数据验证：某份数据是否满足规定条件
业务规则：某种条件下如何判断或处理
行动控制：某个人或系统能否执行某项动作
```

以 OWL 为代表的本体语言通常采用开放世界假设：信息缺失表示未知，不一定表示错误。必填、唯一、封闭字段等验证往往需要 SHACL、数据库约束或代码；某项业务动作能否执行，还要依赖权限、Action 校验、工作流和执行系统。

### 1.6 本体不等于什么

**本体不等于知识图谱。**本体侧重概念模型和语义限制；知识图谱侧重具体实体、关系和断言。两者经常结合，但不能简单互换。

**本体不等于数据库 Schema。**数据库 Schema 首先服务于存储和软件实现；本体首先服务于业务含义。现有表结构不一定代表正确的企业认识。

**本体不等于数字孪生。**本体可以提供语义基础；数字孪生还需要对象状态、映射机制及按用途接入的仿真、预测或反馈能力。

**本体不等于因果模型。**图中存在关系或时间先后，不能直接证明因果。可靠因果仍需来自物理机理、明确制度机制、干预实验或因果识别。

**本体不等于 Agent。**本体描述 Agent 面对的业务世界；Agent 负责理解任务、选择工具、组织步骤和发起受控行动。

**本体不等于真理。**它是企业在特定目的下建立的选择性模型，可能包含制度安排、管理选择和局部惯例。

## 二、企业为什么需要本体

### 2.1 串联系统，建立共同业务语义

企业系统通常围绕局部流程建设。相同名称可能代表不同口径，不同名称也可能指向同一对象。本体可以明确：

- 哪些概念必须采用共同定义；
- 哪些领域可以保留局部定义；
- 不同定义之间如何映射；
- 哪些冲突尚未形成共识。

这不是强迫所有部门使用完全相同的语言，而是在局部业务边界内形成稳定语义，在跨边界处建立明确映射。

### 2.2 为 Agent 提供稳定上下文和行动边界

本体让 Agent 不只依赖文字相似性，而能围绕明确对象进行查询和计算：

- 用对象类型、唯一标识和别名减少主体混淆；
- 要求关键关系来自数据或证据；
- 标明规则的适用对象、生效时间、版本和例外；
- 把确定性计算交给数据库、函数和专业模型；
- 把 Actions 与权限、参数校验、确认和回滚连接；
- 在信息缺失、冲突或超出边界时允许返回未知。

这能够压缩错误空间，但不能消灭错误。原始数据、实体对齐、规则、模型和人的判断都可能出错。

### 2.3 建立可溯源和可审计能力

可溯源回答“这项断言从哪里来”，包括：

- 数据或文档来源；
- 产生及转换时间；
- 使用的本体、规则、函数和模型版本；
- 录入、审核和发布责任。

可审计进一步回答“整个判断和行动过程能否被重建”，包括：

- 当时接收了什么任务；
- 使用了哪些证据；
- 比较了哪些方案；
- 哪些权限和前置条件得到满足；
- 是否经过人工确认；
- 实际执行了什么动作；
- 状态如何变化；
- 是否发生异常、撤销或纠正。

本体可以定义这些审计对象及其关系，真实审计证据仍需由身份认证、运行日志、版本管理、证据保存和工作流共同产生。AI 自己生成的理由说明不能直接作为完整审计证据。

### 2.4 显化经验，形成组织学习闭环

企业关键知识往往散落在制度、代码、公式、审批习惯和少数专家经验中。把其中高价值、需复用、需审计且错误代价较高的部分显式化，可以降低人员变化带来的知识流失。

人的经验首先只是候选知识，不能未经验证就成为正式规则。系统应记录其来源、适用范围、例外、时间和责任，再通过数据、案例、专家评审和实际反馈持续校准。

### 2.5 本体不能独立解决或保证的问题

本体不能：

1. 保证知识真实、完整和及时；
2. 自动完成数据清洗、实体对齐和系统集成；
3. 消除所有歧义或完整形式化人的隐性知识；
4. 从图结构中自动产生可靠因果知识；
5. 替代流程模拟、运筹优化、控制算法和专业软件；
6. 消灭大模型错误或单独保证行动安全；
7. 仅凭模型结构形成真实、可信的审计系统；
8. 一次建设后永久有效；
9. 用技术方式自动解决组织权责和利益冲突。

## 三、从静态对象到动态企业

### 3.1 对象、状态、事件和过程

企业不是静态对象的集合，而是在事件、活动和行动中持续变化的系统。

| 层次 | 回答的问题 | 示例 |
|---|---|---|
| 对象 | 企业中有什么 | 客户、订单、设备、组织 |
| 状态 | 对象现在怎样 | 库存、负荷、审批状态 |
| 事件 | 发生了什么 | 下单、故障、制度发布 |
| 过程 | 状态如何连续变化 | 采购、生产、审批、交付 |

企业通常擅长保存最终状态，却不一定能把事件、过程、规则、责任和结果统一组织起来。业务事件、审批轨迹、操作日志和时间序列都能记录过程；困难在于这些记录经常分散在不同系统中，没有被解释成可复用知识。

### 3.2 数据如何产生，与数据本身同样重要

除了“这个数据是多少”，还要追问：

- 它由什么活动产生；
- 活动使用了什么输入和证据；
- 哪些规则、模型和外部条件影响结果；
- 谁在什么角色下承担责任；
- 它何时产生、何时有效；
- 后续是否被修订或推翻。

W3C PROV-O 使用 Entity、Activity 和 Agent 等概念表达实体、活动和责任之间的来源链。Process Mining 则从事件日志中发现、检查和改进实际业务过程。这些能力可以与企业本体结合，但不是本体结构自动产生的。

### 3.3 系统必须区分不同知识状态

| 知识状态 | 含义 | 示例 |
|---|---|---|
| 原始记录或观测 | 系统、文件或传感器记录的内容 | 交易记录、温度采样 |
| 经确认的企业事实 | 由有权主体确认的当前断言 | 当前正式负责人 |
| 制度或规则 | 对行为和判断的规范性要求 | 审批权限、指标口径 |
| 系统推导 | 根据显式规则得到的结论 | 根据授权关系推导审批人 |
| 模型估计或预测 | 由统计或机理模型产生 | 故障概率、需求预测 |
| Scenario 假设 | 为比较方案设定的临时状态 | 假设港口关闭七天 |
| 专家判断 | 人在证据不完备时作出的决定 | 是否停机检修 |
| 候选知识 | AI 抽取或人员提出、尚未确认 | 候选职责关系 |
| 未知或冲突 | 信息缺失或来源不一致 | 两份制度权限不同 |

如果不区分这些状态，预测可能被误当成事实，假设可能写回现实，AI 抽取结果也可能未经确认进入正式知识。

### 3.4 时间、来源和冲突必须显式表达

严肃业务至少要区分：

- 事件何时发生；
- 系统何时记录；
- 断言从何时生效、何时失效；
- 某次判断使用了哪个版本；
- Scenario 代表哪个假设时间点。

来源冲突时，系统不应静默覆盖，而应保留各自来源、时间、权威等级、当前采用项、裁决责任和待确认状态。置信度可以帮助排序候选，不能替代正式责任。

### 3.5 从决策到行动，再从结果回到模型

一个完整学习闭环至少包括：

```text
问题与目标
+ 输入与证据
+ 规则和模型版本
+ 关键假设
+ 候选方案
+ 责任主体
+ 实际行动
+ 结果指标
+ 后续评价和纠正
```

这条链使企业不仅保存“做了什么”，还能够理解“为什么这样做、结果是否有效、原来的认识是否需要修改”。

### 3.6 企业“第二大脑”是组合体系，不是一个本体文件

```text
本体模型：描述对象世界
事件和过程：描述如何变化
规则和模型：描述如何判断
决策和行动：记录为什么这样做
结果和反馈：检验原来的认识
```

它们共同连接起来，才可能形成企业的组织记忆和学习能力。无差别保存全部对话、文件和 AI 内部自述只会重新制造信息膨胀；应优先保存能够承担责任、支持复用和重建判断的结构化记录。

## 四、本体如何与模型、Agent 和行动结合

### 4.1 不同知识与模型承担不同职责

| 能力 | 主要回答的问题 |
|---|---|
| 语义公理 | 对象和关系在逻辑上意味着什么 |
| 数据验证 | 某份数据是否满足规定条件 |
| 业务规则 | 什么条件下如何判定或处理 |
| 机理模型 | 改变变量后状态按什么机制演化 |
| 统计或机器学习模型 | 未知状态或未来结果可能是什么 |
| 优化模型 | 在目标与约束下哪种方案更优 |
| 人的判断 | 在不完整信息和价值冲突下承担决定 |

对象被画成图，不代表系统自动获得因果推演、预测或优化能力。

### 4.2 本体提供推演世界的语义骨架，但不是推演本身

| 能力 | 回答的问题 |
|---|---|
| 本体 | 世界中有哪些对象、关系和限制 |
| 状态数据 | 世界现在怎样 |
| 业务规则 | 什么条件下如何判定或行动 |
| 机理模型 | 状态按照什么机制演化 |
| 统计模型 | 未知或未来状态可能是什么 |
| Scenario | 改变条件后形成怎样的假设世界 |
| 优化模型 | 哪种方案更优 |
| Actions | 如何改变真实业务状态 |
| Agent | 如何调用能力、比较方案和解释结果 |

```text
现实数据 → 当前业务世界
              ↓
       规则、机理、统计和优化模型
              ↓
         Scenario 假设世界
              ↓
        AI 与人比较方案
              ↓
        受控行动与结果反馈
```

这里的“沙盒”是围绕特定决策建立的选择性表达，不是覆盖企业全部现实的完整镜像。

### 4.3 Agent 是任务协调者，不是企业完整大脑

LLM 是模型；Agent 是由模型、指令、状态、工具、权限和执行循环组成的系统。

在企业场景中，Agent 更适合：

- 将自然语言转化为业务对象查询；
- 在权限范围内检索数据和文档；
- 调用规则、函数、机理模型和优化工具；
- 解释结果并绑定证据；
- 必要时发起受控动作；
- 遇到未知、冲突和高风险情况时请求人工判断。

AI 可以提供带证据、可比较、可追溯的建议；人负责确定目标、处理价值冲突、审核高风险建议并承担最终责任。形式上的“人工审核”不天然保证安全，审核者还必须能够看到证据、理解差异并拥有真实否决权。

### 4.4 Actions 使系统从描述企业走向改变企业

Actions 表达可以对对象执行的业务操作，例如创建订单、修改状态、建立关系、提交审批或写回业务系统。

Actions 不等于规则、机理模型或 SHACL：

- 规则和 Functions 决定如何计算、判断或编排；
- SHACL 等机制验证数据是否满足条件；
- Actions 定义可以发起什么业务变化；
- 权限和工作流决定谁能在什么条件下执行；
- 日志说明实际发生了什么。

行动能力必须与最小权限、参数校验、人工确认、运行监控、异常停止和回滚共同设计。

### 4.5 MCP 是连接协议，不是数据层或本体层

MCP 让模型应用发现和调用外部资源、提示和工具。企业可以通过 MCP Server 暴露本体查询、规则计算、文档检索或业务 Actions，但不存在一种独立的“MCP 数据”。

```text
数据与证据
→ 本体及可操作语义层
→ 查询、规则、模型和 Actions
→ 通过 API、MCP 或其他接口供 Agent 调用
→ 受控行动与反馈
```

MCP 不自动定义业务语义，也不自动解决数据质量、实体对齐、权限和行动安全。

### 4.6 管理域与工业域的计算逻辑不同

管理域关注对象、制度、职责、审批、权限和协同：

```text
数据与文档 → 业务语义 → 规则与函数 → Agent → 工作流与 Actions
```

工业域关注物理对象、实时状态、机理、预测、优化和控制：

```text
设备与工艺语义 → 实时数据 → 机理/统计模型 → 仿真优化 → 人或控制系统执行
```

两类能力可以共享对象标识、来源、时间、权限和审计机制，但不能把管理规则当成工业机理，也不能把工业仿真直接套到组织管理。

### 4.7 企业人工智能主权：关键能力可控，而非所有技术自研

企业人工智能主权，是企业对关键 AI 资产、运行环境和技术选择保有实质控制权，能够按照自身目标独立部署、评测、运行、升级、回滚、停止、迁移和替换，而不因单一供应商、平台或外部服务中断而失去关键业务能力。

人工智能主权至少包括：

| 主权维度 | 企业需要掌握的能力 |
|---|---|
| 数据与语义主权 | 控制企业数据、本体、规则、知识和反馈记录的访问、使用、审计与导出 |
| 模型主权 | 掌握所用模型、权重或服务依赖、微调参数、系统配置、评价基线和版本，能够验证、替换与回滚 |
| 运行主权 | 控制算力、存储、网络、身份权限、密钥、日志、Agent 编排和部署环境 |
| 供应链与退出主权 | 识别芯片、框架、模型、组件、许可证和外部服务依赖，并具备替代、迁移和灾难恢复方案 |
| 治理主权 | 企业拥有发布、停用、授权、风险接受和责任认定的最终决定权 |

“完全掌握模型参数和运行基础设施”可以作为高主权等级的重要要求，但不能单独代表人工智能主权。只把开源模型下载到本地，如果企业仍然无法解释依赖、评测效果、修复问题、完成迁移或维持关键业务运行，也没有形成实质控制。

主权要求应与场景风险相匹配。普通办公辅助可以在数据、合同和权限受控的条件下使用外部模型；涉及核心工艺、生产控制、重大经营决策和敏感数据的系统，应采用更高等级的模型、运行环境和供应链控制，并明确断网、降级和供应商退出条件下的连续运行方案。

主权的目标不是封闭，而是保有选择权。企业可以采购外部模型、平台和专业服务，但不宜外包自身业务语义的定义权、关键运行能力和最终治理责任。

### 4.8 AI 系统需要持续演进与安全运行

企业本体智能不是一次建设后长期不变的静态系统。模型能力、软件组件、攻击方法、法律要求、业务规则和企业环境都会变化，因此必须建立覆盖开发、测试、发布、运行、修复和停用的持续工程机制。

```text
外部技术、业务与风险变化
            ↓
候选模型、组件、规则和配置更新
            ↓
离线评测、安全测试与兼容性验证
            ↓
审批、灰度发布与运行观察
            ↓
异常发现、停止、降级、人工接管或回滚
            ↓
根因分析、修复验证与经验回写
```

持续更新不是追逐所有新模型，而是持续识别与企业任务有关的技术变化，通过统一能力问题、测试集、风险指标和成本指标，与现有基线比较后决定是否采用。更新对象不只包括大模型，还包括本体、规则、Prompt、记忆、Skill、工具、专业模型、Agent 工作流和基础软件。

安全也不能只保护数据入口或模型 API，而应覆盖：

- 数据、本体、规则、模型和训练或反馈材料；
- Prompt、记忆、Skill、工具、Agent 与 Actions；
- API、MCP、业务系统接口和数据管道；
- 算力、操作系统、容器、网络、存储和终端；
- 身份、权限、密钥、人工审批和审计日志；
- 开源组件、模型来源、许可证和软件供应链；
- 开发、测试、发布、运行、停用和销毁的完整生命周期。

运行中应持续观察准确性、稳定性、时延、成本、数据与模型漂移、提示注入、越权调用、工具失败和异常行动。出现问题时，系统应能够保存现场、定位影响范围、停止或隔离高风险能力、切换降级方案或人工流程，并在修复验证后受控恢复。

### 4.9 从问题诊断到企业运行指导

企业本体智能的目标，不只是回答企业发生了什么，而是围绕企业目标持续理解当前状态，发现问题，分析原因和影响，调用规则与专业模型推演方案，并在权限范围内指导或发起行动。

| 企业活动 | AI 可以支持的能力 |
|---|---|
| 生产运行 | 识别异常、瓶颈、计划偏差和连锁影响，提出处置建议 |
| 设备维护 | 诊断故障、判断风险、安排检修窗口、人员和备件 |
| 经营管理 | 分析订单、客户、收入、成本、库存、现金流和经营风险 |
| 资源调度 | 协调人员、设备、产能、物料、物流和时间，比较调度方案 |
| 决策与行动 | 比较收益、成本、风险和约束，生成建议、提交审批或调用 Actions |
| 反馈校准 | 根据行动结果修正规则、模型、本体和后续策略 |

共同工作链条可以概括为：

```text
业务目标
→ 感知企业当前状态
→ 发现异常或目标差距
→ 沿本体关系诊断原因和影响
→ 调用规则、机理、预测与优化模型
→ 推演和比较候选方案
→ 形成带证据、约束、风险和不确定性说明的建议
→ 人工确认或权限范围内受控执行
→ 观察结果并持续校准
```

本体为这条链提供共同对象、关系、口径、规则边界和责任结构，使 AI 能够把分散的业务信号解释为同一问题中的状态、原因、约束和行动对象。

但建立本体不等于自动获得全部经营和调度能力。只有在可靠数据、实时事件、业务规则、专业模型、目标函数、权限和行动接口具备的条件下，企业本体智能才可以支持生产运行、设备维护、经营管理和资源调度，并逐步从辅助判断发展到受控行动。AI 可以辅助诊断和提出方案，重大价值冲突与高风险行动仍应由有权主体判断并承担责任。

## 五、什么情况下值得建设，以及如何评价

### 5.1 判断重点是问题结构，不是企业规模

| 判断因素 | 程度越高通常意味着什么 |
|---|---|
| 跨系统程度 | 同一问题需要穿透多个系统和文档 |
| 语义冲突程度 | 相同名称存在不同口径 |
| 关系复杂度 | 判断依赖多层对象关系 |
| 约束密度 | 存在较多规则、权限和例外 |
| 决策风险 | 错误可能造成安全、合规或经济损失 |
| 行动要求 | Agent 需要修改状态或触发流程 |
| 审计要求 | 必须说明使用了什么依据 |
| 知识流失风险 | 关键知识集中于少数专家 |
| 复用价值 | 同一对象和规则被多个应用使用 |
| 维护条件 | 存在负责人和机制维护模型 |

### 5.2 更适合显式本体的场景

- 跨系统对象对齐和主数据语义统一；
- 合规审计、制度校验和权限管理；
- 复杂供应链、设备、组织和产品关系穿透；
- 需要把专业规则、函数和 Actions 提供给 Agent；
- 需要保存历史状态、来源和责任链；
- 多个 Agent 或应用共享同一业务对象模型。

### 5.3 不宜过早建设重型本体的场景

- 普通文档问答、总结、翻译和个人提效；
- 数据和流程较小，人可以直接掌握全貌；
- 规则少、错误成本低；
- 业务仍在高速探索，概念频繁重构；
- 没有明确责任人维护定义和规则；
- 只是追随技术热点，没有具体业务问题。

这些场景可以优先使用文档、RAG、数据表、Workflow、Skill 或普通 Agent。轻量方案并不低级。

### 5.4 用能力问题评价，而不是用概念数量评价

建设前应列出可验证的能力问题，例如：

- 某项职责当前由哪个组织承担，依据是什么；
- 某个岗位是否有权审批这类事项；
- 某项制度变化影响哪些流程、指标和角色；
- 某个供应商中断会影响哪些产品；
- 当前结论使用了哪个规则版本和数据来源。

如果模型不能稳定回答目标问题，增加更多概念不会自动提高质量。

### 5.5 最低评价维度

| 维度 | 需要检查的问题 |
|---|---|
| 目的适配 | 是否支持目标业务问题和行动 |
| 概念清晰 | 定义、边界和局部口径是否明确 |
| 区分能力 | 能否处理同名、别名和边界案例 |
| 约束有效 | 是否能配合验证机制发现真实错误 |
| 证据完整 | 是否保留来源、时间和责任 |
| 计算边界 | 规则、因果、预测和人的判断是否区分 |
| 行动安全 | Actions 是否具备权限、确认和回滚 |
| 自主可控 | 关键数据、语义、模型和运行环境是否可控制、迁移、替换和退出 |
| 运行韧性 | 是否具备持续监测、安全更新、降级、人工接管、回滚和恢复能力 |
| 可维护性 | 是否有负责人、版本和变更分析 |
| 实际价值 | 减少的错误、时间或风险是否超过成本 |

模型还应通过信息缺失、来源冲突、制度失效、跨域口径不一致、预测失败、越权行动和 Scenario 被误当成现实等反例检验。

### 5.6 最小但有用

本体的质量不是抽象程度越高越好，也不是覆盖越广越好。更合理的目标是：

> **用尽可能小的显式结构，承载那些不宜仅交给概率模型、不能只留在人脑、又确实值得长期维护的企业知识。**

## 六、组织治理与华泰当前基础

### 6.1 本体不是中立的技术资产

“客户”“收入”“责任部门”“有效制度”等定义可能直接影响考核、权限、责任和资源。本体可以暴露冲突、记录分歧和支持协商，但不能用技术手段自动解决组织政治和管理选择。

关键定义必须有提出、审核、发布、申诉和修订机制。

### 6.2 需要区分不同责任

| 责任角色 | 主要责任 |
|---|---|
| 业务语义负责人 | 确认概念、口径、边界和例外 |
| 数据负责人 | 确认来源、质量、主数据和状态同步 |
| 规则负责人 | 确认规则含义、生效时间和变更 |
| 模型负责人 | 确认适用范围、版本、评价和失效条件 |
| Action 负责人 | 确认权限、前置条件、回滚和责任 |
| 运行负责人 | 确认可用性、容量、监测、发布、降级、回滚和灾难恢复 |
| 安全负责人 | 识别全生命周期风险，确认安全基线、漏洞处置、供应链与事件响应 |
| 本体与平台团队 | 负责形式化、映射、工具和运行能力 |
| 治理主体 | 处理跨域冲突、重大变更和高风险发布 |

一人可以承担多个角色，但这些责任不能在概念上混为一体。外部团队可以提供方法和工程能力，企业对自身业务语义的定义权和持续维护能力不宜完全外包。

### 6.3 华泰当前基础

现有“华泰组织与职责本体 v0.1”已经把组织架构图转化为可追溯、可审核的对象和关系底稿，并区分原始事实、规范解释、置信度、歧义和历史版本。

它目前主要描述静态组织结构，还不能代表完整企业本体，更不能直接称为数字孪生。人员任职、职责制度、流程动作、权限约束、业务数据和能力问题是否纳入，需要由具体场景决定。

这份底稿当前最重要的价值是帮助内部理解：本体不是画一张关系图，而是同时保留对象、关系、原始证据、业务解释、分歧、时间和版本。

### 6.4 下一步判断应从能力问题开始

如果后续考虑扩展，首先应回答：

1. 需要支持哪个具体判断或流程；
2. 现有方法为什么不能满足；
3. 必须增加哪些对象、事件、关系和约束；
4. 谁对这些定义负责；
5. 如何评价扩展后的准确性、效率和风险；
6. 如何证明本体相对于文档、RAG、数据表或普通 Agent 具有增量价值。

具体试点范围和实施路线不在本文展开。

## 七、开放问题

1. 随着大模型能力增强，哪些显式结构仍值得长期维护？
2. 什么内容应进入正式本体，什么内容更适合由文档、Skill、代码或专业模型承载？
3. “可追溯”应追溯到数据、规则、模型、系统执行，还是人的最终判断？
4. 企业语义统一到什么程度后，成本开始超过收益？
5. 跨领域概念冲突由谁裁决，如何允许合理分歧长期共存？
6. 本体、业务规则、专业 Functions 和 Actions 的边界应如何划分？
7. 工业场景中语义层与机理模型之间应建立怎样的接口？
8. 推演沙盒中的状态变化分别由规则、机理、统计模型还是人的判断承担？
9. 当本体影响考核、权限和决策时，如何防止模型反过来扭曲真实业务？
10. 华泰应选择哪个能力问题作为第一个可评价的本体试验？
11. 华泰哪些场景必须掌握模型参数和运行基础设施，哪些场景可以在可迁移、可替换的条件下使用外部服务？
12. 如何建立统一评测和发布机制，使 AI 技术持续更新而不破坏现有业务的稳定性与安全性？
13. 在运行、维护、经营和调度中，哪些问题适合由 AI 提示，哪些可以受控执行，哪些必须保留人的最终决定？

## 附录 A：Palantir 产业参照

### A.1 Palantir Ontology 的定位

Palantir 当前从系统层面把 Ontology 表达为 Data、Logic、Action、Security 的组合，以 Objects、Properties、Links 描述业务对象，以 Actions 和 Functions 连接业务逻辑与操作。

它是面向企业决策和运行的复合系统，不只是传统 OWL/RDF 形式本体；但也不应笼统等同于数字孪生、因果模型或仿真系统。

Palantir 所说的 `Kinetic` 更接近改变对象和推动流程的行动能力，不等同于物理机理；`Dynamic Security` 是贯穿对象、函数和动作的安全机制，不应被理解为独立的动态数据层。

### A.2 Actions、Functions、Models 与 Scenario

- Actions 创建、修改、删除或连接对象，并可写回业务系统；
- Functions 承担业务逻辑、计算和编排；
- Models 估计、预测或优化对象属性；
- Scenario 是从当前 Ontology 数据分出的假设状态，通过 Actions 和 Models 比较不同方案。

这些能力相互连接，但不能与本体结构本身混为一谈。

### A.3 AIP Evolve

AIP Evolve 不是一种新大模型，也不等于本体自动演化。它在目标、验证策略和修改约束下，协调多个 AI FDE Agent 改进 Foundry 中的 AI 系统。

```text
目标资源
→ 优化目标
→ 测试方法和基线
→ 允许修改的范围与迭代次数
→ Agent 探索候选修改
→ 与基线进行评测
→ 形成证据和 Proposal
→ 人审核后决定是否合并
```

它主要优化模型选择、Prompt、Guardrails、工作流、工具调用和系统配置，而不一定修改大模型权重。可以把它理解为：

> **以评测为反馈、以多个 Agent 为搜索者、以受控修改为行动空间的系统级迭代优化。**

从 Harness 角度看，它相当于使用一套更高层 Harness，约束 AI FDE Agent 改进业务 Agent 及其 Harness。

### A.4 日志、观察与审计

Palantir 相关能力包括：

- Action Log：把 Action 提交和相应决策记录为 Ontology 对象；
- Edit History：保存对象修改历史；
- Object Timeline：观察人和 Agent 对对象的操作、归因和执行指标；
- Ontology/AIP Observability：观察函数、Action、Agent、模型和工作流执行；
- Audit Logs：服务于安全、合规和责任追踪。

本文不把它们统称为官方产品意义上的“Ontology Logs”。日志也不会自动产生最佳实践，必须与结果指标、人工标注、评测和复盘机制连接。

## 附录 B：帮助理解的比喻与个人场景

### B.1 本体是一种有目的的语义压缩

Stewart Brand 用“信息既渴望昂贵，也渴望自由”概括信息传播成本下降与高价值信息之间的张力。真正昂贵的往往不是信息数量，而是把分散信息组织成可以理解、验证、复用和行动的知识。

本体可以被理解为一种有目的的语义压缩：它不是容纳所有信息，而是从具体问题出发，提取需要长期区分和维护的对象、关系、规则、来源和责任。

这种压缩可以降低语义混乱和协同成本，形成长期认知资产，暴露隐含假设，并显化部分专家经验。但任何压缩都会损失信息；本体必须保留来源、时间、分歧和未知。

“抵抗熵增”可以作为比喻，但不是严格的信息论结论。没有责任人、版本管理和持续校准的本体，本身也会成为新的混乱来源。

### B.2 从“皮”到“骨架”

过去，AI 更多看到企业呈现出来的“皮”：文档、报表、界面、语言和结果。本体试图把相对稳定的“骨架”显式告诉 AI，包括对象、关系、定义和约束。

但 AI 仍然需要“皮”，因为数据、事件、文档和人的表达是感知现实变化的证据。更准确的方向是：

> **让 AI 用骨架理解“皮”，用“皮”校准骨架，并识别两者之间的不一致。**

骨架也不是企业唯一、永恒的本来面目，而是围绕特定问题建立的、稳定但可修订的选择性模型。

| 身体比喻 | 企业智能中的对应能力 |
|---|---|
| 骨架 | 对象、关系、定义和语义限制 |
| 皮肤与感官 | 文档、数据、传感器、事件和用户输入 |
| 肌肉与器官 | 规则、专业模型、流程和执行系统 |
| 神经系统 | 数据管道、事件流、API 和 MCP |
| AI | 信息处理、方案生成和任务协调 |
| 人 | 目标设定、价值判断和责任承担 |
| 免疫系统 | 权限、安全、审计、验证和异常停止 |

### B.3 本体与 Agent Harness

企业本体智能可以被理解为 Agent Harness 的重要组成，但形式本体本身不等于完整 Harness。

> **本体告诉 Agent 它身处什么世界，Harness 告诉 Agent 它在这个世界里能怎样工作，目标告诉 Agent 这一次要解决什么问题。**

完整 Harness 还包括系统指令、任务状态、运行循环、工具适配、权限、日志、评测、异常处理和反馈机制。

### B.4 个人知识库

当个人笔记、文档和对话远超上下文容量时，可以围绕人物、项目、观点、来源、任务、决策和时间建立轻量对象关系模型，帮助 AI 按任务取得材料，而不是一次读完所有记录。

个人知识库不一定需要重型形式本体。能够显式表达对象、关系、来源和任务边界，往往已经可以产生价值。

### B.5 程序员与代码 Agent

让 AI 生成的代码符合某个程序员或团队的习惯，主要依赖项目 Harness：仓库上下文、架构说明、接口、依赖关系、编码规范、优质示例、类型系统、Lint、测试和评审要求。

本体思想可以帮助表达模块、服务、接口和架构约束，但不能保证 AI 写出的代码与本人完全相同。目标应是符合项目结构、能够通过验证并且易于理解，而不只是表面风格相似。
